# Implementing Cross-Origin Storage (COS): Engineering Notes

> [!NOTE]
> These notes are based on Thomas Steiner's (@tomayac) personal implementation experiments and are not an official position of any browser project or the WICG.

**Sources:** four independent implementations of the [WICG Cross-Origin Storage explainer](https://github.com/WICG/cross-origin-storage) and [spec draft](https://wicg.github.io/cross-origin-storage/) — Servo's, on the `cross-origin-storage` branch of [tomayac/servo](https://github.com/tomayac/servo) (Rust); Ladybird's, on the `cross-origin-storage` branch of [tomayac/ladybird](https://github.com/tomayac/ladybird) (C++); Firefox/Gecko's, on the `cross-origin-storage` branch of [tomayac/firefox](https://github.com/tomayac/firefox) (C++); and Chromium's, as a work-in-progress Gerrit CL against `chromium/src` ([8256403](https://chromium-review.googlesource.com/c/chromium/src/+/8256403)) (C++). None of these has shipped in a released browser. The Servo, Ladybird and Firefox branches are personal experiments; the Chromium change is a first implementation pass on a path Chrome does intend to ship, but it is unreviewed and unlanded. Points specific to one are marked **Servo:**, **Ladybird:**, **Firefox:**, or **Chromium:**; everything else applies regardless of what you're building on.

> [!IMPORTANT]
> Two parts of this document describe designs the spec has since changed, and both changes were made because the original design was exploitable. [§2](#sec-2) now says a create request must register **nothing** (there is no `pending` entry state, and no outstanding-writer count, staleness timeout or generation counter to go with it), and [§4](#sec-4) now says an entry's grants are independent and **additive** (an origins list and a globally-disclosable flag, never one ordered "scope" field). Both sections explain the old design, why it is wrong, and what to test. If you are porting from an implementation written against the older text, start there.

**How to use this document:** read it alongside the spec and explainer, not instead of them. This captures the parts the spec deliberately leaves to implementations ("an implementation-defined maximum length", "could delete files ... based on, for example, a least recently used approach"), pitfalls worth designing against from the start across four independent implementations (several of them security-relevant), and the performance work that turned out to matter once a registry grows to the scale this feature targets — many AI-model shards, potentially multi-hundred-MiB each. Every numeric constant below is an implementation choice, not the spec's; pick your own based on your own browser's precedent, but don't skip picking one — several of these gaps are exploitable if left unbounded.

**On the Public Hash List specifically: it is real, it exists today, and you can download it right now.** [§4](#sec-4)'s Gate 1 below gives the exact fetch URL, the checksum-verification step, and says outright that the pipeline "is now validated by four independent implementations" — that's concrete, actionable detail, not aspirational language. **Read [§4](#sec-4) Gate 1 before you build your own PHL loader.**

This document doesn't try to be a step-by-step tutorial. It's organized by concern, so you can jump to the part you're currently implementing.

## Glossary

Terms as used in this document — some are spec terms, some are implementation vocabulary for things the spec leaves unnamed. Alphabetical; each points at the section with the full explanation.

- **Atomic write** — writing to a sibling temp file first, then `rename()`-ing it into place, so a reader can never observe a half-written file. Relies on `rename()` being atomic on the same filesystem. See [§7](#sec-7).
- **Availability gating** — the read-time decision of whether a given requesting origin is allowed to see a particular entry, based on its disclosure scope. See [§4](#sec-4).
- **Content-addressable (storage)** — a storage scheme where the key *is* a cryptographic hash of the content itself, rather than an arbitrary name the writer chose. Two writers storing byte-identical content always land on the same entry — that's what lets independent origins "share" a resource without either being able to overwrite or corrupt what the other wrote. See [§2](#sec-2).
- **Disclosure grants** — the three independent, additive things that decide which requesting origins, besides the storing origins themselves, are allowed to read a given entry: the same-site baseline every entry carries, an explicit origins list, and a globally-disclosable flag (`'*'`, gated by the PHL + GREASE'ing). Stored as separate fields, never as one ordered scope; see [§4](#sec-4).
- **COS scope ceiling** — the set of origins a write is permitted to name in its `origins` list, taken from the `Cross-Origin-Storage-Allow-Origin` header of the response behind the bytes. The declared list is intersected with it, so script that cannot set a response header cannot widen a disclosure. See [§4](#sec-4).
- **Entry** — one row of the registry: a single stored resource, keyed by its hash, together with its storing origins and its disclosure grants. An entry exists only once its bytes have been supplied and verified; a write that has been requested but not completed has no representation at all. See [§2](#sec-2).
- **eTLD+1 / registrable domain** — "effective top-level-domain plus one label" — e.g. `example.com`, or `example.co.uk` (where `.co.uk` is the *effective* TLD per the Public Suffix List, not a literal one). This is the unit same-site comparisons are made against; you cannot compute it correctly by just counting dots, which is why you need the Public Suffix List (or your engine's equivalent) rather than writing new logic. See [§4](#sec-4).
- **Fingerprinting oracle / side channel** — any observable signal (a response, a specific error type, a timing difference) that lets a page infer something about the user it otherwise has no business knowing — e.g. "was this specific resource ever cross-origin-cached" as an implicit proxy for "has this user visited some other site." Much of this feature's design (GREASE'ing, budget-based-on-total-not-free-disk-space, rate-limit denials that look identical to genuine misses) exists specifically to avoid creating one. See [§4](#sec-4)–[§6](#sec-6).
- **GREASE / GREASE'ing** — deliberately, randomly reporting a resource as absent even though it's genuinely cached and would otherwise be disclosed, for entries qualifying through the global grant that already passed the PHL check. Stops a caller from treating a "found" response as a *reliable* signal. Name borrowed from the unrelated TLS GREASE mechanism (same "deliberately inject noise so nobody can rely on a signal that shouldn't be relied on" idea). See [§4](#sec-4).
- **Origin vs. site** — an *origin* is scheme + host + port (`https://a.example.com:443`); a *site* (for same-site purposes) is scheme + eTLD+1 (`https://example.com`). Two different origins can be same-site (different subdomains or ports of the same registrable domain); same-origin implies same-site, not the reverse.
- **PHL (Public Hash List)** — a curated, cross-vendor, rolling-release allowlist of resource digests confirmed "ubiquitous" and "corroborated" enough that disclosing their cross-origin presence doesn't leak anything meaningful about one specific user. The gate that makes the global grant safe at all. See [§4](#sec-4).
- **Probe** — the spec's own framing for a `requestFileHandle()` read call: since its outcome (found, not found, or still pending) is directly observable by the calling script, every read is implicitly an attempt to learn something about cross-origin state, and has to be rate-limited accordingly, not treated as a free query. See [§5](#sec-5).
- **Quota exceeded** — the rejection outcome when a write can't be accommodated within the storage budget even after every eviction it's entitled to. See [§6](#sec-6).
- **Registry** — this document's name for the whole in-memory-plus-persisted structure mapping hashes to entries, plus the logic operating on it. Not a spec term — the spec only describes the algorithms; "registry" is just a convenient implementation-side name for "the thing that stores and answers questions about entries." See [§1](#sec-1).
- **Resource thread** — **Servo:** the thread/process that already owns other shared, persistent browser state (cookies, HTTP cache, HSTS) and that Servo's implementation also hosts the COS registry in. Your engine's equivalent may have a different name and shape (a shared network service, a browser/UI process, a storage broker — see [§1](#sec-1)) — the point is putting the registry wherever your engine's analogous shared, persistent, non-script-thread service already lives, not the specific name.
- **Revoke-and-GC** — one of two policies for what a site-scoped "Forget This Site"/clear-data action does to a COS entry that site is one of several storing origins for: strip that site's own storing-origin/storing-site/disclosure-grant associations from the entry, and only delete the entry outright if that leaves it with no storing origin left. Contrasted with the alternative, "delete-if-involved" (delete the whole entry regardless of other legitimate owners). See [§16](#sec-16).
- **Secure context** — the Web Platform concept of an origin considered safe enough (HTTPS, or a recognized local exception like `localhost`/loopback IPs) to expose powerful APIs to. COS is `[SecureContext]`-gated in its WebIDL, so it's unavailable from a plain non-loopback `http://` page. See [§12](#sec-12).
- **Sole-owned (entry)** — an entry with exactly one storing origin, as opposed to a *shared* entry that multiple independent origins have each written/verified. An origin hitting its own storage share is only ever allowed to evict its own sole-owned entries to make room — never a shared entry, even one it co-owns. See [§6](#sec-6).
- **Storing origin(s)** — the set of origins that have each independently completed a successful write (`close()`) for a given hash. Distinct from disclosure scope: a storing origin can always read its own write regardless of scope; disclosure scope governs everyone *else*. See [§2](#sec-2).
- **Streaming (write)** — sending a large write's bytes to the registry in a sequence of smaller chunks rather than one giant message, so the registry never holds an entire large payload in memory at once. Independent of whether the writable stream's own buffer (the thing being streamed *from*) is backed by memory or disk — see [§3](#sec-3).
- **Token bucket** — a standard rate-limiting algorithm: a per-key counter that holds up to some maximum number of "tokens," refills continuously over time, and is decremented by one on each allowed action; once empty, further actions are denied until enough time passes to refill at least one token. Used here per requesting origin, separately for reads and writes. See [§5](#sec-5).
- **Cross-origin probe budget** — distinct from a token bucket, and easy to conflate with one. A token bucket limits the *rate* of calls; a probe budget limits the *total number of distinct hashes* a site may ever resolve cross-origin, because each such hash is worth at most one bit to an attacker assembling a cross-site identifier. Its shape and value are under discussion, see [§5](#sec-5).

## 1. Architecture: where the registry lives

COS's registry (the mapping from hash → stored bytes + metadata + disclosure state) needs to be:
- Shared across every tab/worker/process using it (it's cross-origin by definition).
- Persisted to disk across restarts.
- Reachable from script without blocking the calling thread on disk I/O.

**Put it in whatever your engine's existing shared, persistent, IPC-reachable service is** — the thing that already owns cookies, HSTS state, and disk caches. Script-side code is a **thin IPC client only**: it does not own any state, does not implement any spec algorithm, and every function in it sends a message and returns immediately. All the real algorithms — entry state machine, origin-scoping decisions, availability gating, hash verification, quota enforcement — live in that shared service.

**Servo:** this shared service is the *resource thread* — the same process/thread that owns the HTTP cache and the cookie jar, among other shared file-backed state.
**Ladybird:** this is the UI/browser process — the same process that already owns the cookie jar, HSTS store, and other shared persistent state, reached over IPC from each content/worker process.
**Firefox:** a dedicated singleton service living on the PBackground thread in the parent process — Gecko's existing catch-all for exactly this shape of "shared, non-origin-scoped, IPC-reachable, off-the-main-thread" state (it already hosts things like the storage-notification and IndexedDB-adjacent services). Reached via a new, deliberately minimal actor pair (`PCrossOriginStorage`, one `Parent`/`Child` per content process) registered directly under `PBackground`, modeled structurally on `PIdleScheduler` rather than on any of Gecko's *origin-scoped* storage actors (`PQuota`, `PFileSystemManager`) — the explicit reason being the same one this section gives: COS entries are not per-origin, so wiring into an origin-partitioned actor tree would have imported assumptions (directory-lock-per-origin, quota-Client registration) that actively fight what content-addressability needs. Concretely: **don't reach for your engine's existing per-origin storage actor tree just because it's the closest existing precedent** — check whether it depends on per-origin partitioning before extending it, or you'll spend more effort working around that assumption than the reuse saves you.

**Whatever sequence or thread the registry serializes its own work on, do not also hash payloads on it.** The registry's own file work is uniformly short — write a metadata record, unlink a file, rename one into place, `stat()` one to answer a read. Hashing is not: this feature exists for multi-hundred-MiB to multi-GB resources, and a fallback full-file pass over one of those ([§3](#sec-3)) takes seconds. Put them on the same serialized queue and a read's `stat()` waits behind a write's hash, which is a latency regression with no cause a profile makes obvious. **Chromium:** gives each writer a sequenced task runner of its own, distinct from the registry's, so nothing a writer does can delay the registry's decisions. The registry still needs *its* work serialized (that is what the spec's Cross-Origin Storage queue asks for); the point is that hashing is not registry work.

**Before writing a parallel file-handle class, check whether your engine's `FileSystemFileHandle` is a thin wrapper over an IPC interface you can implement yourself.** The spec says to create a real `FileSystemFileHandle`, and the WPT suite asserts `instanceof` on it, so every implementation has to satisfy that somehow. Servo, Ladybird and Firefox each had to do real work here; Firefox in particular could not reuse `FileSystemWritableFileStream` because it couples tightly to `PFileSystemManager`'s fd-passing. **Chromium:** got this nearly free, because Blink's `FileSystemFileHandle` is little more than a wrapper around a `mojo::Remote<FileSystemAccessFileHandle>` — implementing the *browser* end of that existing interface for COS entries (plus `FileSystemAccessFileWriter` for the write side) means the stock Blink class works unmodified, `instanceof` holds by construction, and OPFS internals are never touched. Whether this is available to you is a property of how your engine layered its own File System Access implementation, so it is worth ten minutes of checking before committing to a parallel class hierarchy.

Why this split matters in practice: a Worker has exactly one script thread. If verifying and storing a write blocked that thread for the duration of writing a multi-hundred-MiB file to disk, nothing else on that worker could run for the whole write. **Servo:** on Servo's desktop port, a similar block on a Window's script thread freezes scroll input handling too, because wheel events are dispatched synchronously and are cancelable by script. **Don't put a synchronous, disk-touching operation on any thread that also has to stay responsive to input or other script.**

A workable IPC shape (see [§9](#sec-9) for why "IPC" doesn't necessarily mean serialization overhead):

- Script thread sends a message carrying a callback handle.
- The registry-owning service processes it and invokes the callback (on its own thread, or an IPC router thread in true multi-process mode — never the original calling thread).
- The callback's only job is to queue a task back onto the *correct* script thread to resolve/reject the promise.

**If your engine is multi-process rather than (or in addition to) multi-threaded**, "put the registry on the shared service" understates the work by one layer. A Worker in a multi-process engine doesn't just run on a different thread — it runs in an entirely separate OS process from the main renderer, with its own IPC connection (or lack of one) to wherever the registry lives. **Ladybird:** the Window path was built and verified first; adding Worker/SharedWorker support afterward turned out to be cheap specifically because a per-worker-process IPC connection to the registry's host process *already existed*, for cookies and HSTS — COS's messages just needed to go on that existing wire. If your engine doesn't already have a route like that for something else, budget real time for building one; don't assume "Window vs. Worker" is only a script-level/JS-binding distinction once process boundaries are real.

## 2. Data model & entry lifecycle

One entry per hash, and an entry only ever exists in one state: written. It is added by `verify and store`, once a writer has supplied bytes that hash to the requested value and the user agent has verified them. Before that there is nothing in the registry at all.

```
(nothing)  --(a write verifies and is stored)-->  written
(nothing)  --(a failed, abandoned or never-started write)-->  (nothing)
```

**A create request must register nothing. This is a security property, not a simplification, and an earlier draft of the spec had it the other way round.** That draft created a `pending` entry when a create-backed handle was requested, before any bytes arrived, so that a concurrent `requestFileHandle()` for the same hash could observe "still pending" (a distinguishable `NotAllowedError`) instead of "not found". If you are reading an older implementation, a `pending` state is what you will find. Two things are wrong with it, and they are worth spelling out, because the design reads perfectly reasonable until you look at what it hands an attacker:

- **The distinguishable answer is a free, noiseless oracle for any hash.** Any origin can derive hashes from a per-user value, open create handles for a chosen subset of them on one site, and read that subset back on another. The answer is decided *before* origins scoping, before the PHL, and before GREASE'ing — every disclosure control this feature has lives on the read path, and a pending entry answers ahead of all of them. No bytes are ever written, so the storage limit never bounds it either.
- **An abandoned create handle pins its hash.** A handle that is never written through — `createWritable()` never called at all — still holds the entry pending, which suppresses every other origin's reads of a hash of the abandoner's choosing, indefinitely and for free.

Registering nothing closes both at once, and it deletes a surprising amount of machinery along with them. An implementation built on the pending model needs a per-entry outstanding-writer count (so a failing writer cannot delete a concurrent sibling's entry), a never-written qualifier on that cleanup (so no origin can delete bytes another origin stored by writing garbage under the same hash), a wall-clock staleness timeout (so a page that navigates away mid-write does not wedge a hash), an explicit abandonment signal as a fast path for that timeout, and a per-entry generation counter compared on every settle path (so a late `close()` from a writer whose entry was already reclaimed cannot corrupt the replacement). **None of that is needed once a create request registers nothing:** there is no pending entry to reclaim, no count to settle, no timeout to wait out, and nothing for a stale writer to disturb. A failed write removes nothing because it registered nothing, so the concurrent-writers race that all of the above existed to survive stops being a race at all.

**What still needs care:** the concurrent-writers case does not disappear, it moves. Two writers racing on the same hash each write their own swap file and each verify independently; whichever publishes first creates the entry, and the second joins it rather than adding a second entry or charging the bytes twice. **Create the entry at *publication* time**, re-looking up the hash at that moment rather than deciding earlier, and the second writer merges by construction. **Keep the two-concurrent-writers-one-fails-one-succeeds test** — it is still the case a single-writer-focused suite will not catch, and the spec's own suite has it (`requestFileHandle-create-and-read.*.any.js`).

**`getFile()` on an unwritten create handle still rejects with `NotAllowedError`, and that is not an exception to any of the above.** That gate is per *handle*: a create request returns a handle whether or not an entry exists, and the caller must supply the bytes before it can read through it. Its answer is constant with respect to the registry — the same whether the hash is stored or not — and a handle cannot be deserialized cross-origin, so it crosses no origin boundary and discloses nothing. **Gate reading per handle, never per entry.** A per-entry check passes every ordinary single-origin round trip, because there the handle that wrote the entry is the handle reading it, which is exactly why it is easy to get wrong and hard to notice.

**Extend terminal-failure handling to your own failure modes, not just the spec's literal case.** The spec names one definite failure (a hash-mismatched `close()`). A real implementation has more: a disk I/O failure partway through a write, an unrecognized algorithm, a quota-exceeded rejection at `close()` time, a streaming-time size cap being tripped ([§10](#sec-10)). Funnel them all into one path rather than inventing a cleanup per failure type. Under the current model that path is short — discard the swap file, reject the caller — which is itself a reason to prefer it. **Ladybird** and **Firefox** each arrived at the one-mechanism rule independently under the older model, and it survives the simplification.

**Storing origins and disclosure grants are different things.** An entry tracks:
- **A set of storing origins** — every origin that has independently written/verified this exact hash. (Content-addressability means two unrelated origins can both "write" the same bytes; this is not a copy, it's the same entry gaining a second storing origin. See [§4](#sec-4).)
- **An origins list and a globally-disclosable flag** — two independent, additive grants deciding who, *besides* the storing origins and the origins same site with them, gets to read it. See [§4](#sec-4) for why these are two fields rather than one.

## 3. Content-addressable integrity: the seek()/truncate() ordering constraint

`FileSystemWritableFileStream` (the write side, inherited from the File System Access API/OPFS shape) supports `seek()` and `truncate()` — genuine random-access edits to the in-progress write, at any point before `close()`. A COS hash, meanwhile, can only ever be verified against the **complete, final** byte sequence.

**The one universal consequence, regardless of implementation maturity: you cannot *unconditionally* verify a hash incrementally as `write()` calls arrive.** A later `seek()`/`truncate()` can still invalidate content you've already seen, so the verified digest has to reflect the final state, not whatever streamed past during the writes themselves.

**But "cannot verify incrementally" is not the same as "must always make a second pass," and reading it that way costs real time on exactly the payloads this feature targets.** The overwhelmingly common write is strictly append-only: `createWritable()`, some number of `write()` calls in order, `close()`. For that shape the bytes going past *are* the final state, and a running digest fed chunk by chunk is already correct at `close()`. Only `seek()`, and a `truncate()` to anything other than the length already hashed, actually invalidate it.

So: **keep a running digest, track whether it still describes the file, and fall back to one full pass only when it does not.** A single boolean is enough. Start it true; feed each chunk to the digest as it lands and advance a "bytes hashed" counter; if a write's offset is anything but that counter, or a truncate's length is anything but that counter, clear the boolean and stop updating the digest. At `close()`, finalize the running digest if the boolean is still set, and otherwise re-read and hash the finished file exactly as before. The cost of the fallback is paid only by the writers that actually trigger it, and a gigabyte-scale model shard written the ordinary way never re-reads a gigabyte it just wrote. **Chromium:** does this, on the same object that owns the swap file. Note that this composes with the write-failure flag below rather than replacing it: a running digest computed from bytes you *handed* to the disk is not evidence they landed.

A related win from the same object: **hold the swap file open across chunks.** Re-opening it per chunk is easy to end up with when each chunk write is an independent task, and at a 512 KiB chunk size that is thousands of `open()`/`close()` pairs for one multi-gigabyte write.

What that final state is backed by — and therefore whether "waiting for the final state" costs you application memory or not — depends on what your engine already has and what you choose to build:

- **If you already have a mature, disk-backed `FileSystemWritableFileStream`/`FileSystemFileHandle` implementation** (i.e. real OPFS support, which already needs genuine random-access disk I/O for its own non-COS use cases), you very likely don't have a memory problem at all: back COS's writable stream with that same real, disk-backed temp file, let the OS handle random access, and only read/hash it once, sequentially, at `close()` time.
- **If you're building `FileSystemWritableFileStream` from scratch for COS**, with no OPFS to lean on, build it on a real disk-backed temp file from the start rather than an in-memory buffer (`seek()`/`write()`/`truncate()` all operate on it directly via ordinary file I/O). This sidesteps the entire unbounded-allocation-DoS category in [§10](#sec-10) at the design level, rather than needing a runtime cap on it, and keeps this feature's characteristically large payloads (multi-hundred-MiB to multi-GB) off script-process memory for the duration of the write, not just at the moment they're finally handed to the registry. It isn't entirely free: a temp file opened write-only for streaming needs to be re-opened, or rewound and read, once `close()` needs to hash the final content — a small, one-time cost against avoiding a whole class of bug.

The ordering constraint above (the verified digest must describe the final state) applies either way — it's a property of the spec, not of any particular backing store.

Separately from *that* question — once `close()` is called and the final content is known (in memory or on disk, either way) — you still don't want to send it to your shared registry service as one giant message, nor have that service hold the whole payload in memory either. That transfer is worth streaming in chunks regardless of how the writable stream itself was backed, since the registry service is shared across every tab and origin using the feature, making it the more valuable place to economize regardless. A workable shape is a three-message protocol:

```
begin(session_id, hash, origin, declared_total_bytes)   // no response
chunk(session_id, bytes)   × N                            // no response
finish(session_id, type_string, requested_origins) -> outcome
```

`session_id` is a random client-generated token (not spec-visible; purely an implementation detail for correlating chunks). The begin and chunk messages have no response — only the finish message does, and only it needs to. Chunks arrive in order because they're sent on the same underlying ordered channel, so no sequence numbers are needed. On the receiving side: hash incrementally (update a running digest per chunk) and, if config allows, write each chunk straight to a temp file rather than accumulating in memory; on finish, compare the final digest, and if it matches, atomically publish (rename the temp file into place).

**A bug worth designing against explicitly: the temp-file write for an incoming chunk can fail** (disk fills up mid-write — genuinely realistic for this feature, since it targets multi-GB downloads that can plausibly run right up against free disk space). If a running hash and byte-count get updated *unconditionally*, before attempting the fallible disk write, and a failed write only logs a warning, the finish step's hash check can still pass — it was checking the *intended* bytes' hash, not what actually landed on disk — and the implementation would happily rename a truncated/corrupt temp file into place, mark the entry written, and serve it to every future reader under a hash that no longer matched its real content. That's a silent violation of the one guarantee this entire feature exists to provide.

**Fix:** track write failures explicitly on the session (a simple flag set by the fallible chunk-write step), and check that flag *first* when finishing, before trusting the byte-count or digest checks — neither of those can detect this failure mode on their own, because they're both computed from data that was already accepted into memory *before* the disk write was attempted.

**Ladybird:** built the flag-and-check-first guard in from the start.

**Lesson for other implementers:** if your streaming design reads back from disk to populate any in-memory cache (Servo's implementation does, for its `Arc<Vec<u8>>` read-path cache — see [§9](#sec-9)), that read-back is trusting the disk, and a partial/failed write anywhere upstream of it will silently propagate. Either (a) track and check write failures explicitly, as above, or (b) re-verify size/hash against what you actually read back before trusting it, or both.

**Firefox: chose the memory-backed path deliberately, as an explicit, documented, time-boxed tradeoff.** Gecko had no mature OPFS `FileSystemWritableFileStream` implementation this could reuse for COS specifically (the real one couples tightly to `PFileSystemManager`'s fd-passing, which doesn't fit a non-origin-scoped registry — see [§1](#sec-1)), so a from-scratch write path was needed either way; rather than building a disk-backed temp file for it, the write session holds the entire in-progress write in memory in the parent-process actor, gated by [§10](#sec-10)'s flat size cap (4 GiB, matching this document's own suggested value) — the cap is what makes this choice safe. The write session *is* persisted to disk once complete ([§7](#sec-7)), but the in-progress bytes during the write itself are memory-resident; real disk-backed streaming is a tracked follow-up item, not yet built. **The lesson, independent of which way you decide:** "build the disk-backed version from day one" ([§3](#sec-3)'s own recommendation) is the right target, but if you don't have the runway for it immediately, the safe fallback is *not* "in-memory, uncapped" — it's "in-memory, with the [§10](#sec-10) cap already in place before the memory-backed version ever ships."

**Firefox: the actor wire protocol independently converged on the same three-message shape §3 recommends** (`BeginWrite`/`WriteChunk`×N/`FinishWrite`, plus an explicit `AbortWrite` for the fast-path abandonment case from [§2](#sec-2)) — a third implementation landing on the identical shape is a reasonable signal that it's the right one, not just Servo's or Ladybird's particular convenience.

**Firefox: a JS-engine-binding-specific gotcha not covered by either other implementation, because it's specific to how WebIDL union types get compiled.** The obvious WebIDL type for a writable-stream chunk argument is a `BufferSource` union (`ArrayBuffer or ArrayBufferView`), matching the real File System Standard's own `write()` signature. In this Gecko configuration, the generated binding for the plain (non-`AllowShared`) `BufferSource` typedef turned out not to be usable at the call site that needed it — confirmed only by an exhaustive header search, not by a compiler error pointing at the actual problem. **The fix:** accept `any` at the WebIDL layer instead, and do the type discrimination by hand in native code using the engine's raw JSAPI type-introspection calls (`JS::GetObjectAsArrayBuffer` / `JS_GetObjectAsArrayBufferView` in SpiderMonkey — check `IsArrayBuffer`/`Local<ArrayBuffer>::Cast` or your engine's equivalent otherwise), which unwrap cross-compartment wrappers internally and need no separate manual unwrap step. **Lesson:** if a WebIDL union type you'd expect to "just work" doesn't compile cleanly or silently fails to bind in your engine's specific configuration, don't assume it's a typo in your own `.webidl` file before ruling out a binding-generator limitation for that particular type combination — dropping to raw engine-native type checks on an `any` argument is a legitimate, if less declarative, fallback.

## 4. The three disclosure grants

An entry's visibility can be **upgraded** but never downgraded: a later writer of the same hash can only ever add recipients, and a writer requesting less than what is already granted is a no-op (the spec's "upgrade resource visibility" step).

**Store the grants as independent fields, and never as one ordered "scope" enum.** A single field ordered same-site < list < wildcard is the obvious model, it is what an earlier draft described, and it is wrong. The three grants are:

1. **The same-site baseline**, which every entry carries unconditionally: the storing origins, and every origin same site with one of them.
2. **An origins list**, initially empty, which only grows.
3. **A globally-disclosable flag**, initially false, which only ever becomes true.

They are checked in that order, and **the order is the point**: only the third consults the PHL and GREASE'ing. Collapse them into one enum and an `origins: "*"` write *replaces* an existing list, at which point every origin on that list starts getting `NotFoundError` whenever the hash is not on the PHL — a later writer, supplying nothing but the correct bytes, silently revokes access an earlier writer granted. That is a downgrade, dressed as an upgrade, and it is invisible in any test where the hash happens to be listed. **Test it with content that is deliberately *not* on the PHL**: write list-scoped, then write `"*"`, then read from the listed origin. Under the one-enum model that read fails; under the two-field model it succeeds, and the global grant is added alongside. The reverse case is worth pinning too: a list written *after* the entry is already globally disclosable must be added without withdrawing the global grant.

The same reasoning settles a smaller question the enum model gets wrong in the other direction: **an explicit empty list (`origins: []`) grants exactly what omitting `origins` grants.** Under an ordered enum it reads as "list-scoped with nobody on the list", which sounds like it should withhold the entry from the writer's own site; under additive grants it adds no recipient and the same-site baseline is untouched, which is what the spec says and what a caller passing a computed, sometimes-empty array will expect.

### The same-site baseline (what a write with no `options.origins` asks for)

Every entry is disclosed to any origin **same-site** with *any* storing origin — not same-*origin*, and regardless of any other grant. Use the same same-site logic your cookie jar already has for `SameSite=Lax/Strict` (Public Suffix List-backed eTLD+1 comparison): `https://a.example.com` and `https://b.example.com` are same-site (same registrable domain, different origins); `https://example.com` and `https://example.co.uk` are not, despite the superficially similar names. **Reuse your existing same-site helper rather than writing a new one** — this is exactly the same computation your cookie implementation already needs to get right.

### The origins list — `options.origins` is an array of origin strings

- The list has an **implementation-defined maximum length** (the spec explicitly calls this out, precisely so a list can't function as an undeclared substitute for `'*'`). 100 is a reasonable choice — both Servo's and Ladybird's implementations use it. Enforce this in *two* different places, because the spec treats them differently:
  1. A single `requestFileHandle()` call whose own `options.origins` already exceeds the max: throw `TypeError` synchronously, before attempting any write.
  2. *Merging* a new call's origins into an already-list-scoped entry (a second, independent writer declaring more origins) exceeding the max: **not an error** — per spec, silently evict the least-recently-used excess origins instead. This can happen with zero misbehavior from any single caller: independent origins can each write the same byte-identical resource (e.g. a shared open-source library) with their own small `origins` list, and those lists organically merge over multiple write events.
- Track the list as an **LRU structure**: a plain ordered list where position *is* the recency signal (front = least-recently-used) is enough — you don't need separate timestamps per listed origin. A successful *read* by a listed origin moves it to the back. Merging a *re-declaration* of an already-present origin does **not** move it — only an actual read refreshes recency, otherwise a writer could keep a dormant origin artificially "alive" forever just by repeatedly re-declaring it in new writes without it ever actually being used.

### The global grant (`options.origins === '*'`) — the interesting one

A globally-disclosable entry is **not** disclosed to everyone unconditionally. Two independent gates both have to pass, and both apply to *this grant alone* — an origin that already qualifies through the same-site baseline or the origins list has been disclosed before either one is reached:

**Gate 1 — the Public Hash List (PHL).** This is the privacy mechanism the whole feature rests on. Without it, the global grant would be a trivial cross-site tracking/probing oracle: site A writes `sha256(some-value-only-known-if-you-visited-site-B)` with `origins: '*'`; site A later probes for that exact hash from any other context and learns whether the user visited site B. The PHL closes this by only ever disclosing a globally-disclosable entry if its hash is **independently confirmed present on a curated, cross-vendor, rolling-release allowlist** of "ubiquitous, corroborated" resource digests — modeled directly on the Public Suffix List's own governance precedent (per the spec/explainer's framing: cross-vendor governance, not any single browser's list). A hash not on the list **fails closed**: it's simply not disclosed, indistinguishable from a genuine miss. The PHL only lists SHA-256 digests, so a globally-disclosable entry hashed with any other recognized algorithm (SHA-1/384/512) can never pass this gate — check the algorithm before even attempting the lookup.

  Implementation-wise, the pipeline below is now validated by four independent implementations, not just one browser's particular choice:
  - The PHL is generated and published in the spec's own repo: `WICG/cross-origin-storage`, under `public-hash-list/implementation/`.
  - **It's tracked via Git LFS.** `raw.githubusercontent.com` only serves the LFS *pointer* text (a few hundred bytes: `version .../oid sha256:.../size ...`), not the actual multi-tens-of-MB file. You need `media.githubusercontent.com/media/<owner>/<repo>/<ref>/<path>` (GitHub's LFS media endpoint) to get the real content for a public repo.
  - **Verify a checksum after downloading it.** The PHL repo publishes a companion `<file>.sha256` (standard `sha256sum`-compatible format, itself LFS-tracked too — fetch it the same way) right next to the data file. Fetch that first, then pin the big file's download against the hash it gives you, rather than checking it as an afterthought — this guards against a corrupted/truncated transfer or a compromised LFS response landing in something that ships to every user, and turns a bad transfer into a loud build failure instead of silently-wrong compiled-in data.
  - The raw `.dat` format is **not one undifferentiated list — it's three sections with different adoption requirements**, delimited by `// ===BEGIN SHA-256===`/`// ===END SHA-256===`-style comment markers (comment lines otherwise carry provenance annotations only, safe to ignore for parsing): a core section (real-world-popularity-corroborated: CDN request volume, npm downloads, cross-CDN byte-identity, browser-vendor vetting) a user agent **MUST** treat as eligible; a Hugging Face model-hub section a user agent **SHOULD** include and **MAY** omit (it qualifies entries on a different, non-popularity basis — "published on a recognized public model hub" — since a specific AI model build can be hugely valuable to deduplicate yet appear on only a handful of sites, so it would never clear the core section's popularity threshold; the tradeoff is coarser: this section only discloses "this user runs in-browser AI models," not a specific site, and the spec repo's own docs note adoption only pays off if it's uniform — an implementation that omits it forces those large downloads to repeat per origin while one that includes it doesn't, handing a real, uneven performance advantage that runs against the PHL's whole point as a neutral resource); and a hand-curated manual-additions section (reviewed via pull request against the same ubiquity bar) a user agent **MUST** also treat as eligible. **Decide your policy on the middle tier explicitly** — don't just concatenate all the digest lines from every section into one array without having actually made that call, even though nothing forces you to notice the distinction if you script the parsing casually.
  - Re-encode the digest lines from whichever section(s) you adopt at build time into **sorted, packed 32-byte binary digests with no delimiters**, purely to keep the compiled-in resource compact and to enable `binary_search` (O(log n)) at lookup time instead of needing a `HashSet` (a `HashSet<[u8; 32]>` of hundreds of thousands of entries costs meaningfully more memory for the same guarantee, and the list is read-only after load, so a sorted array is strictly better here). Sort once, at generation time, so nothing needs to re-sort it again every process startup.
  - **A resource this size can be a compile-time problem in its own right, independent of everything above.** At real scale (roughly 295,000 entries across all three sections combined, as of one snapshot — this is a rolling-release list and the exact count grows over time; core alone accounts for the large majority), spelling it out as a source-level array literal is tens of millions of characters of text for the compiler to parse, just for this one file — slow at best, and a real risk of hitting a compiler/tooling limit at worst. Two genuinely different fixes, not just one:
    - **Compile it in**, via whatever raw-binary-embed facility your toolchain has: C23's `#embed`, a linker/assembler `incbin`-style directive, or your language's equivalent — the generated source stays small and fast to compile no matter how large the list gets, since the bytes are pulled in directly rather than spelled out as syntax.
    - **Firefox: don't compile it in at all — ship it as a plain external data file alongside the browser binary, loaded once at runtime.** Packed at ~9.4 MiB (295k × 32 bytes), even a binary embed facility isn't free (it still makes this translation unit responsible for a multi-MB resource, and not every toolchain's embed support is equally mature); registering the packed file via the build system's existing "ship this file next to the installed binary" mechanism (Gecko: `FINAL_TARGET_FILES`) and reading it back with one lazy, on-first-lookup file read (resolved relative to the installed binary's own directory, not the user's profile — this is compiled-application data, not per-user state) sidesteps the compile-time question entirely, at the cost of a fallible runtime file read instead of a guaranteed-present compiled-in resource (fail safe to "nothing loaded" on any read error, exactly like a genuinely empty list — never crash, never treat a load failure as "everything is on the list"). Which of the two approaches fits better depends on how good your specific toolchain's embed story actually is and how comfortable your build system is shipping loose data files next to the binary; both get you out of the "tens of millions of characters of source" problem.
  - **Memory-map it rather than reading it in, if your platform lets you.** The list is read-only after generation, already sorted, and searched by binary search, so a mapping is exactly the right shape for it: the search touches the handful of pages it visits and nothing else, which means the file costs address space instead of ~14 MiB resident *per profile*, and a browser whose user never reaches the global grant pays nothing beyond the mapping. It also removes the read itself from startup. Validate the mapping's size and shape after mapping rather than before — mapping reserves address space and reads no pages, so rejecting an implausibly sized file that way costs nothing. Fail closed on any error exactly as a read would. **Chromium:** maps both the list and its provenance companion this way. The same applies to any companion data you ship beside the list.
  - **Load it off the thread that answers requests, and not lazily on first lookup.** The obvious design — read the packed file the first time a global-grant lookup needs it — puts a multi-MiB blocking read directly inside the availability-gating decision, on whatever thread that decision runs on. **Chromium:** that thread is the browser's UI thread, where a blocking read trips the engine's own "no blocking here" assertion outright; the fix was to read the file on the registry's file sequence during its existing async startup, alongside loading persisted entries, and to queue any request that arrives before initialization finishes rather than answer it against an empty registry. Even where it does not trip an assertion, a ~9.5 MiB synchronous read on a latency-sensitive thread is not something to do at an arbitrary moment chosen by whichever site happens to probe first. Answering requests against a not-yet-loaded list is the other trap: it silently reports every globally-disclosable entry as absent for as long as the load takes.
  - **Keep it current** — it's an explicitly rolling-release list, not a one-time snapshot; the spec's governance model depends on it being kept current. Three genuinely different approaches, only two of which are actually adequate:
    - **Servo:** a scheduled CI job re-runs the fetch/verify/re-encode pipeline periodically (weekly) and commits the refreshed, compiled-in snapshot into the browser's own repository — whatever a given build embeds is exactly whatever was last committed, reviewable like any other change.
    - **Ladybird:** fetches and verifies directly from the upstream source at build-configure time instead, with no separate scheduled job of its own — a given build is always as current as upstream's default branch was at the moment it was configured.
    - **Firefox: neither, yet — a one-time, manually-triggered snapshot, with no refresh mechanism of any kind.** The generation script was written, run once by hand against a downloaded-and-checksum-verified `.dat` file, and its output committed; nothing re-runs it. This is explicitly named here as the **inadequate** option, not a third valid choice alongside the other two: a PHL that never refreshes is a PHL that slowly drifts stale relative to the upstream list's own governance-intended cadence, with no mechanism — scheduled or build-triggered — to notice or correct that. It was an acceptable stopgap for getting *real* data in place at all (replacing an empty seed is still strictly better than shipping none), but treat "we integrated the PHL" and "we keep the PHL current" as two separate, both-necessary milestones — hitting the first is not evidence you've hit the second, and it's easy to declare victory at the first one and never come back to the second.
    - The tradeoff to know about the two adequate approaches either way: neither continuously refreshes an *already-configured* build tree. A build-time-fetch design like Ladybird's still needs a clean checkout or a cleared build cache to actually pick up a newer list, not just a recompile; a checked-in-snapshot design like Servo's is only as current as the last time its scheduled job actually ran and its commit actually merged. "Automatic" doesn't mean "instant" under either design — budget for that when reasoning about how stale a given user's compiled-in list could plausibly be. A design that ships the list as an external runtime-loaded resource rather than compiling it in (see above) doesn't change this tradeoff at all — it only changes *how* the refreshed bytes get into a build, not *when* or *how often* that happens.

**Gate 2 — GREASE'ing.** Even *after* an entry passes the PHL check, occasionally lie and report it as absent anyway, chosen at random per read. (GREASE: "Generate Random Extensions And Sustain Extensibility" — the spec's own term, borrowed from TLS.) The point: a caller must never be able to treat a reliable "found" response as *proof* a resource is cached, because that itself would be a timing/existence oracle for whatever content the caller is probing for. If "found" is always 100% reliable when it's true, an attacker can use presence/absence as a precise signal; occasional false negatives break that guarantee without breaking the feature's main performance benefit (which only needs "found" to be *usually* reliable to be worthwhile).

The spec constrains this qualitatively: **"must NOT GREASE responses for files whose size makes a spurious re-download clearly disproportionate to the privacy benefit."** A numeric threshold (500 KiB) below which GREASE'ing is eligible, and a probability (1%) for eligible entries, is one reasonable choice — used by all four implementations (Firefox and Chromium copied Servo's and Ladybird's constants directly rather than independently re-deriving them, which is a fine choice given the spec itself gives no numbers to converge on independently — there's no reason to introduce needless cross-implementation variance in a constant the spec deliberately left open). Get the *reasoning* right even if you pick different numbers: a false negative on a small file just costs a cheap re-fetch; on a large one (the spec's own example is gigabyte-scale AI model weights) it would impose a real, observable bandwidth/latency cost — and that cost difference is itself observable (a "found but GREASEd" response is distinguishable from a genuine miss by its retry latency), which would undermine the whole point of GREASE'ing. **Never GREASE large entries.**

**Firefox:** the roll itself uses the engine's OS-sourced cryptographic RNG (`mozilla::RandomUint64OrDie`, the same primitive available for exactly this "needed before NSS is necessarily initialized, must not be predictable" situation), not the engine's general-purpose fast PRNG (the one `Math.random()` ultimately bottoms out on, or your engine's internal equivalent). This matters for the same reason the size ceiling does: a *predictable* GREASE roll is not a GREASE roll at all — if an adversary can predict or bias which requests get GREASEd, the false-negative noise stops being noise and the "found" signal becomes reliable again through the predictable gaps. **Use your engine's cryptographic RNG for this specific decision, not whatever RNG is fastest or most convenient** — this is exactly the kind of detail that's easy to get wrong silently, since a fast-but-predictable PRNG produces output that looks statistically fine in every ordinary test and only fails the actual security property under adversarial analysis.

### The `Cross-Origin-Storage-Allow-Origin` ceiling — bounding the list at write time

The origins list is declared by script (`options.origins`) or by markup. Both are things an attacker who has achieved script or markup injection on the writing page can set, and a disclosure to an origin of the attacker's choosing is exactly what they would set it to. The response header is what ties the declaration to the operator of the origin whose bytes are being disclosed, in a form injected content cannot forge: **`Cross-Origin-Storage-Allow-Origin` carries a set of origins, the declared list is intersected with it, and anything the header does not name is dropped.**

Five things to get right, most of which fail quietly if you don't:

- **Read it on the trusted side of your process boundary, from your own record of the response.** Not from the renderer/content process, and not from anything script can reach. The whole value of the header is that it comes from the operator rather than from the page, and a design that has the untrusted side report its own ceiling gives that away for free. **Chromium:** the browser process reads it from the last committed response of the relevant document; the renderer never sends it.
- **It comes from the response behind the *bytes*, which is not always the document's.** For `requestFileHandle()` the bytes may be generated in script and have no response of their own, so the calling global's document is the right answer. For the declarative integrations the bytes *do* have one — the fetched resource's response, from a server that need not be the document's — and that is the one to read. Getting this backwards for the integrations authorizes the wrong operator.
- **For a worker, resolve through the owner set and intersect.** A dedicated worker's ceiling is its ancestor document's; a shared worker's is the intersection across its current clients, which come and go, so resolve it per request rather than capturing it when the binding is created. An empty owner set is an empty ceiling. This mirrors the spec's Permissions Policy check, which resolves through the same owner set: one owner that does not authorize an origin withholds it for the whole worker, exactly as one owner that disallows the feature disables it for the whole worker.

  **The same resolution is what decides service workers, and the answer there is "no".** A `ServiceWorkerGlobalScope`'s owner set is empty, so the permission check returns false and every `requestFileHandle()` call from one rejects with `NotAllowedError` — before hash validation, before any registry lookup. This is deliberate and worth implementing as such rather than skipping: a service worker's registration outlives the client that registered it, the user agent starts the global in response to events, and one running global serves many clients whose policies need not agree, so there is no owning document whose policy could be consulted. Covering service workers properly needs a policy captured from the worker's own script response, which is work for [permissions-policy] and [service-workers] rather than for this feature. Until that exists, refusing is the one answer that cannot be used to escape an opt-out. **If your engine exposes the manager on `WorkerGlobalScope` generally, remember that this includes service workers**, and add the explicit refusal — a policy check that consults the global's own inherited policy will happily return true there and hand a service worker the feature. **Chromium:** rejects in the renderer and registers no browser-side binder for service workers at all, so a compromised one cannot reach the registry either.
- **The whole header fails closed on anything unparseable, including `"*"`.** A token that does not parse to a non-opaque origin does not get skipped — it empties the ceiling. `"*"` in particular is not a permitted value: a ceiling of "any origin" would let injected content name any recipient it liked, which is precisely what the header exists to stop. Unbounded disclosure is reached through the `origins: '*'` grant, which is gated by the PHL and never consults this header.
- **A dropped origin is not an error.** The write still succeeds; only the unauthorized disclosure is withheld. If every named origin is dropped, the list is empty and the entry falls back to the same-site baseline. **Log a console warning naming each dropped origin** — this is the one part of the feature where correct behavior and a developer's expectation differ silently, and without the warning they see a narrower entry and no reason for it.

Note the direction, which is the opposite of `Access-Control-Allow-Origin`: there, the server holding a resource opts in to an origin reading it. Here the supplier of the bytes bounds who may later read them out of the shared store, and the origins named are not consulted and send nothing.

## 5. Rate limiting / abuse resistance

> [!IMPORTANT]
> **The concrete read-probe numbers that used to be here have been removed.** They specified a
> per-origin token bucket with a burst capacity of 2000 and a refill of 20/second, sized around
> legitimate sharded-AI-model loading. Those numbers were a *throughput* limit, and they were being
> read as this proposal's privacy defense, which they were never derived to be: 2000 binary queries
> is ample to identify a user. That critique, and the replacement, are being worked out in
> [#72](https://github.com/WICG/cross-origin-storage/issues/72) and
> [#73](https://github.com/WICG/cross-origin-storage/pull/73). Do not implement a number from this
> file until that settles.

**Every read is a probe.** The explainer says this explicitly: "each call to `requestFileHandle()` can be considered a probe." A found/not-found outcome is directly observable by the calling script, so an origin could otherwise brute-force many hashes to fingerprint what's cross-origin-cached.

Two distinct limits are in play, and conflating them is what went wrong here:

- **Rate limiting** bounds how *fast* an origin can probe. It is worth having as ordinary abuse resistance, and a per-origin token bucket is the right shape for it. It does not bound how *much* an origin ultimately learns, because entropy accumulates across visits and a rate limit resets.
- **A probe budget** bounds the *total* number of distinct hashes a site can resolve cross-origin, which is the quantity that determines how wide an identifier an attacker can build. This is the privacy mechanism. Its shape and value are under active discussion in the issues linked above.

Whichever is being enforced, one rule holds in both cases: **when over budget, respond exactly as if the entry were absent (a genuine miss), not with a distinct "rate limited" signal.** Hitting the limit must not itself be an observable, distinguishable event, or the limiter becomes its own oracle (a caller could binary-search for the limit itself, or use "am I being rate-limited yet" as a side channel).

**Writes need their own, separate budget.** A `create()` call has no return value at all (per spec — it's fire-and-forget from script's perspective), so it isn't a *fingerprinting* oracle the way reads are, and it is not charged against the probe budget. But it's still real, unbounded registry churn and disk I/O if flooded — every write that follows one persists bytes and a metadata record. Share one write budget between `create()` and the eventual write-verification step (`close()`), since `create()` is just the first step of a write attempt: spending it on `create()` calls correspondingly reduces what's left for the write that would normally follow, so the abuse is still bounded either way without needing two separate counters. This budget is ordinary flood protection rather than a privacy mechanism, so it can be sized generously.

**Cap the limiter's own memory.** This is the kind of thing that's easy to miss on a first pass, because it's not part of the spec at all — it's purely an implementation detail that can still become a real, unbounded memory leak. If your bucket map is keyed by requesting origin with no eviction, a long-running browser session that visits many different sites will grow that map by one entry per distinct origin **forever**, for the life of the process — unlike the registry itself, which the spec-mandated (and self-imposed budget) caps already bound. Cap the map at some generous-but-bounded number of distinct origins, and when a genuinely new origin arrives at capacity, evict whichever bucket was least recently touched (a bucket's own "last refill" timestamp already doubles as a recency signal for free, since every consumption attempt — success or denial — updates it). Worst case for an evicted origin is a reset burst, equivalent to what it'd see after a process restart — not a correctness problem, just a memory bound. Note that this reasoning does **not** transfer to a probe budget, whose state must persist rather than being evictable at the implementation's convenience.

## 6. Storage budget & eviction

Not spec-mandated in any specific numeric shape — the explainer only mentions LRU-based eviction under storage pressure as *one possible* approach. Real browser precedent for the Storage API generally (per [MDN's storage-quotas page](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)) is a reasonable anchor: Chromium/Safari allow up to ~60% of **total disk capacity**; Firefox's own *existing* Storage API implementation (QuotaManager, backing IndexedDB/OPFS/localStorage/Cache API) is more conservative (10%, capped at a fixed group limit). The more generous 60% figure fits COS well, since it explicitly targets much larger content (multi-GB AI model weights) than typical Storage API usage — all three COS implementations use 60%/20% (see the two-tier breakdown below), including Firefox's own COS work, which deliberately does *not* reuse its own Storage API's more conservative figure, on the reasoning that COS's target content size is categorically different from what that 10% figure was tuned for.

**Base the budget on total disk capacity, not currently-available free space.** This matters for two independent reasons:
1. **Fingerprinting.** Free space changes as *other, unrelated* things fill up the disk. If the budget (and therefore what gets reported in a `QuotaExceededError`) tracked free space, a page could infer real-time free-disk-space information it otherwise has no business knowing, just by triggering deliberate over-quota writes and reading the reported number. Total capacity is stable and reveals nothing about current disk state.
2. **Self-cannibalizing feedback loop.** If the budget were based on free space, COS's own growth would shrink its own future budget, compounding.

Still check **real, currently-available** free space too, as an **internal-only safety net** — the nominal total-capacity-based budget can still nominally "allow" a write that genuinely won't fit right now. But: **never surface the real free-space number to script**, for the exact fingerprinting reason above — report the same stable nominal budget on rejection either way, so a rejection caused by genuinely low disk space is indistinguishable from an ordinary nominal-budget rejection.

**Two-tier budget, not one:**
- **Global cap**: a stable fraction of total disk capacity (60% is a reasonable choice).
- **Per-origin share**: a fraction of the *current* global budget that any single origin's own storing-origin usage may occupy (20% is a reasonable choice, meaning up to 5 origins can each hold a full share before the global cap itself becomes the binding constraint). This exists so **one origin writing a lot can never force eviction of a *different* origin's data** merely by being more recent. Once an origin hits its own share, further writes only ever evict that *same* origin's own **sole-owned** entries (never a shared entry, even one it's a co-owner of, and never another origin's entry) — if that's not enough to make room, the write is rejected with `QuotaExceededError` rather than reaching into someone else's data.
- Only when several *different* origins, each individually within their own share, collectively still exceed the global cap does eviction fall back to plain **cross-origin LRU** — fair in that case, since it reflects genuine multi-tenant demand rather than one origin crowding out another.

**Firefox:** implements this as two explicit passes run in order after every successful write — (1) if the writing origin now exceeds its own share, evict *that origin's own* sole-owned entries, oldest-read-first, until back under its share or out of sole-owned entries to evict; (2) if the registry is *still* over the global cap afterward (pass 1 wasn't enough, or the pressure came from other origins entirely), evict any entry, oldest-read-first, regardless of owner. The concrete platform API for "total disk capacity" was `nsIFile::GetDiskCapacity` — already used internally by Firefox's own QuotaManager for its own (more conservative) budget computation, including the same defensive sanity ceiling described next. **Worth adding regardless of your specific platform API:** cap the *computed* budget itself against a hardcoded absolute ceiling (Firefox: 100 GiB), independent of the percentage math, as a defense specifically against a misreporting platform API — if `GetDiskCapacity`-equivalent ever returns a wildly incorrect value (a known real failure mode on some storage hardware/driver combinations), a pure percentage-of-capacity budget would silently inherit that error instead of failing safe to something bounded.

**Firefox: attributing storage-budget usage becomes genuinely ambiguous once an entry has more than one storing origin, and this document's model doesn't fully resolve it.** The two-tier design above implicitly assumes usage can be cleanly attributed to *one* origin per entry, which is only strictly true for a sole-owned entry. Firefox's implementation resolves the ambiguity by attributing an entry's full byte cost to whichever origin's write *first* transitioned it to written — a second, later origin independently writing the identical byte-identical content (a legitimate, spec-supported scenario — see [§2](#sec-2)) does not add a second charge against the global total (correct: the bytes are genuinely shared, charging twice would double-count real disk usage), but also does not get any budget charged against *its own* share for having stored it (arguably less correct: that origin genuinely does now have a storing-origin relationship to those bytes, with zero budget impact attributed to it). Firefox and WebKit both made this simplification; WebKit's notes record it as a conscious one.

**Chromium resolved this, and in doing so found that the fractional/shared attribution scheme this section used to suggest is unsafe.** Do not split an entry's cost across its storing origins. If an entry of size *S* with *N* storing origins charges each of them *S/N*, then an origin's own charge *falls* when some other origin independently stores bytes it also stores. No API reports usage directly, but an origin can probe its own remaining headroom — attempt a write of known size, see whether it is rejected — and so learn that *somebody else stored this hash*. That is precisely the cross-origin disclosure the Public Hash List, GREASE'ing and availability gating exist to prevent, arriving through the quota system where none of those controls are consulted. It is the same shape as the create-handle read oracle: a side path around the gating rather than a hole in it.

**Charge every storing origin the entry's full size instead, and keep the global total counting each entry once.** The two tiers answer different questions and should not share an accounting model: the global cap protects real disk, so it must count bytes once; the per-origin share is an anti-flooding fairness control, so it should measure what an origin asked the registry to keep — which is what the specification's [storage limits](https://wicg.github.io/cross-origin-storage/#storage-limits) section already describes, "the total number of bytes an origin may contribute to the COS registry through successful writes". The per-origin charges then deliberately sum to more than the bytes on disk, which is correct rather than double-counting, because they are not measuring disk.

This is simpler than either alternative, not just safer. Per-origin usage becomes a pure function of "which entries does this origin store", so:

- An origin's usage depends only on its own writes. No cross-origin coupling exists to leak through.
- It is derivable from the storing-origins set, so there is no attributed-origin field to persist and nothing that can drift out of step. **Chromium** dropped the field from its on-disk metadata entirely (a format version bump) and recomputes usage from storing origins at startup.
- [§16](#sec-16)'s site-scoped clearing stops being a special case: removing an origin from an entry's storing origins gives that origin back exactly what it was charged, and touches no one else. The stale-credit problem disappears rather than needing separate reattribution logic.

**The tradeoff to make consciously:** an origin that stores many already-popular entries burns its own share without adding any bytes to disk. Combined with the rule that an origin over its share may only evict its own *sole-owned* entries, such an origin can reach its cap holding little it is permitted to evict, and get `QuotaExceededError` sooner than a naive reading of "it added no disk usage" would suggest. This is defensible — it genuinely does hold a storing relationship to all of it — but it is the part reviewers will question, so decide it deliberately.

**Eviction order** is oldest-*read*-first (not oldest-*written*-first): track a per-entry "last successfully read" timestamp, updated on every genuine cache-hit read (not on a write, and not on a write that merely re-verifies already-stored content) — an entry a writer keeps re-verifying but nobody ever reads should still be evicted before one that's actively serving readers. Persist this timestamp so eviction order survives a restart accurately.

**The streaming-time quota gap is bigger than it looks.** The budget check above only runs once, at `close()`. But nothing stops a script from calling `truncate(hugeNumber)` *during* streaming — no bytes need to cross the wire at all ([§3](#sec-3)) — growing the real on-disk temp file arbitrarily before that check ever fires. You can't just call the real quota-check/eviction function per chunk to guard against this either: that function can evict *other, already-verified* entries to make room, which is wrong to do on behalf of a write that's still unverified and might yet fail its own hash check at `close()`.

**Fix this with a separate, cheap, read-only bound, distinct from the real budget check:** computed once at write-session start (so it's not a syscall per chunk), then compared against the temp file's actual size after every `write()`/`truncate()` (a `truncate()` sets the tracked size directly; a `write()` only ever grows it up to the resulting stream position). A breach fails the session the same way a disk I/O failure already does ([§3](#sec-3)), reusing the existing cleanup path rather than inventing a new one. The bound itself can be as simple as a flat, generous ceiling (chosen well above any real individual shard size your other budget constants are sized around), or as precise as the live per-origin budget fraction the real check uses — the latter catches an over-quota write sooner, at the cost of needing that fraction available at write-session start rather than only at the authoritative check. This specific gap applies most directly to a disk-backed writable stream; a memory-backed one is already covered by whatever cap you put on `seek()`/`truncate()`-triggered allocation ([§10](#sec-10)).

**Performance, at scale.** Two mistakes that are invisible at unit-test scale and become real bottlenecks once the registry grows to hundreds of thousands of entries (this feature's actual target scale):
- **Don't compute total-bytes-used or per-origin-bytes-used by scanning every entry.** That's an O(n) scan on *every single write*. Maintain running totals instead, updated incrementally at every mutation site (write, evict). O(1) read on every check. Only recompute from scratch once, at startup, when loading persisted entries from disk. **Firefox:** running totals, incrementally maintained.
- **Don't collect-and-sort every candidate entry on every eviction pass.** That's O(n log n) per eviction with no incremental structure. Maintain an ordered index (a sorted set keyed by `(last_read_timestamp, hash)` — the hash breaks ties when your timestamp resolution is coarser than your write rate, which it usually is) that eviction can just walk from the front. O(log n) per removal instead of O(n log n) per pass. **Firefox's eviction index is still a full-entry-list scan-and-sort (O(n log n) per pass) — a known, open gap.** Both of these are easy to get wrong on a first pass and worth a dedicated check before considering storage-budget code done.

## 7. Persistence design

Whatever mechanism you pick, the property you're chasing is the same: **a metadata-only mutation should cost O(1) relative to registry size, not O(n)** — you never want to be rewriting something proportional to everything else stored just to persist one entry's state change or read-recency timestamp. Two real approaches:

**Servo: per-entry files, not one big registry file.** Two sibling files per entry, both named after a filesystem-safe form of the registry key (`"ALGORITHM:hex_value"` with `:` replaced): `<key>.json` (metadata: state, disclosure scope, storing origins, timestamps) and `<key>.bin` (raw bytes, only once written). This gets the O(1)-relative-to-registry-size property directly: a metadata-only mutation (e.g. a fresh pending entry) never has to touch — or rewrite — any entry's bytes, and vice versa. It's also what makes it *affordable* to persist the read-recency timestamp ([§6](#sec-6)) on every single read, which you want for accurate eviction order across restarts but would be far too expensive if every read required rewriting the whole registry. Load at startup by scanning the directory for metadata files; a missing/corrupt bytes file for an otherwise-valid metadata entry should degrade gracefully (treat as absent), not crash the browser.

**Ladybird: SQLite-backed metadata**, since an embedded SQL database was already in use for other shared, persistent browser state (cookies, history). An ordinary indexed `UPDATE`/`INSERT` gets you the same O(1)-relative-to-registry-size mutation cost, without needing to invent your own crash-safe metadata file format or directory-scan-based startup loading logic — the database already gives you both. Blob *bytes* still live as real files on disk either way (don't put large binary content in the SQL database itself). This is a genuine tradeoff, not a strictly better approach: it only makes sense if that database tool already exists in your engine for something else — it's not worth standing up a database dependency just for this.

**Firefox: per-entry files too, structurally closer to Servo's approach than Ladybird's** (no embedded SQL database was already in use anywhere convenient for this), but content-addressed by directory rather than by a sanitized flat filename: `<base>/<algorithm>/<hex-value>.bytes` and `<base>/<algorithm>/<hex-value>.meta`, a subdirectory-per-algorithm layout rather than encoding the algorithm into the leaf filename. Metadata is a small hand-rolled fixed-format binary encoding (via whatever length-prefixed-primitive binary stream helpers your platform toolkit already provides for exactly this purpose — Gecko: `nsIBinaryOutputStream`/`nsIBinaryInputStream`) rather than JSON, mostly because JSON serialization wasn't already a one-line convenience in this codebase for a plain non-JS-exposed C++ struct — pick whichever your own platform makes closer to free. One deliberate scope-limiting choice worth calling out explicitly: **only `written` entries are persisted at all; a `pending` entry's in-progress bytes live purely in memory** ([§2](#sec-2)/[§3](#sec-3)) **until `close()` succeeds**, and losing an in-flight write across a crash or restart is treated as acceptable, matching this document's own framing that "a session that begins a streamed write and then crashes before finishing leaves exactly this kind of orphan" — the difference here is there's no orphan *bytes* file to clean up at all in that case, only a possible orphaned `.tmp` rename artifact (see the Atomic writes paragraph below), since pending-write bytes never reach disk in the first place. This is a smaller scope than a fully crash-recoverable in-flight-write design, traded deliberately for not needing any partial-write recovery logic whatsoever.

**Atomic writes**, regardless of which metadata approach you use. Every persisted file — metadata, and (for a non-streamed write) entry bytes — must survive a crash or power loss without ever being observed half-written by a reader. Standard pattern: write to a sibling temp file first, then `rename()` into place. `rename()` on the same filesystem is atomic on every platform that matters, so a reader always sees either the complete old content or the complete new content, never a torn write. Name the temp file uniquely enough that two different entries' writes can never collide (e.g. based on the final filename), and — separately — clean up any leftover `.tmp` files found during the startup directory scan (a session that begins a streamed write, per [§3](#sec-3), and then crashes before finishing leaves exactly this kind of orphan behind; it's always safe to discard on next launch, since the finish step never happened to publish it). **Firefox:** hand-rolled this rename-into-place helper rather than using the platform toolkit's own built-in "atomic/safe output stream" convenience wrapper (Gecko: `NS_NewAtomicFileOutputStream`) — that wrapper's own internal temp-file naming isn't predictable from the caller's side, which matters specifically for the orphan-cleanup half of this paragraph: reliably *recognizing* an orphaned temp file at startup needs a temp-naming scheme the loading code can predict and match against (a simple `<final-name>.tmp` sibling), not just a scheme that's internally consistent for the writer alone. **If your platform's "atomic write" convenience API doesn't expose or guarantee its temp-file naming scheme, check whether your startup-scan orphan cleanup can actually rely on it before assuming the convenience wrapper gets you this section's full atomic-write property for free** — atomicity of the write itself and *discoverability* of an abandoned attempt are two different guarantees, and a convenience wrapper built for the first doesn't necessarily give you the second.

**Firefox:** the metadata reader's string-deserialization helper (`nsIBinaryInputStream::ReadCString()`) requires the underlying stream to support segmented reads (`ReadSegments()`); a raw local-file input stream unconditionally lacks that capability, so wrap it in a buffered stream first. This is deterministic, not a race or a rare timing issue: it fails on *every* metadata read on any platform/configuration where it applies — the write path never touches it (writes use the plain, unsegmented write primitive, not the read-side's segmented-read requirement), so it's only observable once something actually reads a previously-written entry back. **The general lesson:** persistence code needs a test that spans a real process restart against real on-disk state — a passing build and a passing in-process test suite can both stay green while the reload-from-disk path is completely broken, since neither ever exercises it (a full spec-conformance test suite run within a single browser process never restarts that process, so it never exercises "start up, load what a *previous* process session persisted" at all). If your platform toolkit has a remote-automation/scripting protocol capable of launching-and-relaunching your actual browser against a fixed profile directory (see [§12](#sec-12)), that's the right tool for this specific check — a unit test that mocks the file I/O layer would not catch this, since the bug is in the *real* I/O layer's actual behavior, not in this code's own logic.

<a id="sec-8"></a>

## 8. Concurrency & locking

Match your locking strategy — or lack of one — to your actual concurrency model; don't default to one out of habit.

**Servo:** the registry lives behind a single shared reader-writer lock, matching the shape of its other existing shared, persistent services. Taking the exclusive/write lock for every operation just because *some* paths need to mutate is genuinely harmless if you truly have only one thread ever calling into the registry (contention-free either way) — but the lock type no longer means what it says, and it becomes a real bottleneck the moment registry message handling is ever parallelized for throughput. **The rule: take a shared/read lock first for any branch that doesn't end up mutating anything** (not-found, denied-by-disclosure-gating, or a create request, which now registers nothing at all), and only escalate to the exclusive lock on the specific branch that actually needs to write. Re-decide from scratch under the escalated lock rather than trusting what the shared-lock read observed — the two lock acquisitions aren't atomic together, so treat it as a genuine check-then-act race even if, in your current architecture, nothing can actually race in practice yet.

**Ladybird:** check whether you actually have the concurrency problem above before solving it. Its registry lives in a single process whose access to it is all dispatched synchronously on one event loop (every IPC message is handled to completion before the next one starts) — genuinely single-threaded access, not just single-threaded *today by convention*. No locking scheme was added at all. Servo's advice above is about real concurrent access; a lock that's never actually contended is pure overhead, and — more to the point — building one you don't need can misdirect where you spend implementation effort that would matter more elsewhere.

<a id="sec-9"></a>

## 9. IPC/transfer efficiency

If your engine's script-to-shared-service transport can distinguish "same process" from "true multi-process," take advantage of it for read results: wrap the returned bytes in a reference-counted handle rather than a deep copy, for the in-process case. In true multi-process mode this is never worse (crossing a real process boundary requires copying the bytes somewhere regardless), but in-process it turns every cache hit's transfer into a cheap pointer/refcount bump instead of a full byte-for-byte copy of a potentially multi-hundred-MiB payload. You still need one genuine owned copy eventually, once you actually construct a `File`/`Blob` object from the bytes for script to consume — but that's one copy, on the far side of the transfer, not one copy *per hop*.

**Servo:** does this with `Arc<Vec<u8>>` for its in-process read-path cache. Watch for a specific footgun if your language has both a cheap "clone the smart pointer" and an expensive "clone the underlying data" operation with easily-confusable names/syntax: `Arc<Vec<u8>>::clone()` clones the `Arc`, not the `Vec`, and the two are trivially easy to write by accident where you meant the other. Audit every call site that needs a genuinely independent, mutable, owned copy versus one that just needs to hold a reference a bit longer.

**Ladybird:** this optimization doesn't apply — its architecture is always genuinely multi-process, with no same-process embedding mode at all. Every read result crosses a real process boundary regardless, and needs a real copy/serialize either way, so there's no in-process fast path to build in the first place.

## 10. Security pitfalls

Worth a dedicated security-focused review pass specifically for these — normal development is not reliably going to surface them on its own.

1. **Path traversal via an unvalidated hash for non-default algorithms.** If your hash-shape validation only fully validates the *default/most-common* algorithm's value format (e.g. only checking that a SHA-256 value is exactly 64 lowercase-hex characters, because that's the algorithm your own test suite happens to exercise), and you use the hash `value` string as part of an on-disk file path for *any* recognized algorithm, an attacker can supply a `value` containing path traversal sequences (`../../etc/whatever`) for one of the *other* recognized algorithms and have it read from or written to outside your intended storage directory. **Validate the exact expected digest-length-and-hex-charset shape for every single algorithm your implementation recognizes, not just the one you tested against.** **Ladybird** and **Firefox:** both build full per-algorithm validation in from the start, before any storage-path-touching code exists.

2. **Unbounded resource claim via `seek()`/`truncate()`.** Because random-access edits are allowed before `close()` ([§3](#sec-3)), a page can call `truncate(hugeNumber)` — or `seek(hugeNumber)` followed by any `write()` — and have the writable-stream sink claim an arbitrarily large amount of whatever resource backs it *immediately*, synchronously, from a single script call, long before your registry's own storage-budget check ever gets a chance to reject anything at `close()` time. A memory-backed sink turns this into an immediate allocate-and-zero-fill of an arbitrary size — a straightforward out-of-memory denial of service. A disk-backed sink ([§3](#sec-3)) turns it into unbounded disk space claimed ahead of the real budget check instead (see [§6](#sec-6)'s streaming-time quota gap) — a strictly less severe failure mode, but still one that needs its own guard. Either way: **cap whatever resource a single `seek()`/`truncate()` call can claim, and check that cap *before* attempting the resize/write, not after.** A flat, generous ceiling (e.g. 4 GiB, well above any real individual shard size this feature's other budget constants are sized around) is the simplest version of this cap; tying it to the live per-origin budget fraction instead ([§6](#sec-6)) is more precise but requires that fraction to already be available wherever the write session starts.

   **Firefox:** the fix matches the "flat, generous ceiling" version above (4 GiB) exactly, checked before the resize/write is attempted and reusing the [§2](#sec-2) outstanding-writer-count cleanup path on trip. This is easy to miss on a first pass because nothing else fails without it — no test goes red, no crash occurs, the feature works correctly for every legitimate input. This is exactly why it needs a dedicated security-focused review, not just ordinary feature testing.

3. **Validate at the boundary that's actually trusted, not the one that's convenient to code at.** This is a different bug from #1 above, not a restatement of it: #1 is about validating some algorithms but not all of them, in one place. This one is about validating *correctly, for every algorithm* — but only in a less-trusted renderer/content process, never re-validated in the more-privileged process that actually owns the registry and builds filesystem paths from the hash. If your engine has a real trust asymmetry between a content/renderer process and a more-privileged coordinating process, and your registry lives in the privileged one, a compromised or simply buggy renderer can speak your IPC protocol directly — bypassing whatever validation lives in your WebIDL/script-binding layer entirely, in as few IPC calls as it takes to reach a create request. **Never assume a message reaching your trusted-side registry handler already passed validation somewhere upstream; re-validate anything used for filesystem-path construction at the point it actually crosses into the trusted process.**

   **A successful write path often self-validates the hash shape as a side effect** (it has to match a genuinely-computed digest at `close()`) — **but failure and staleness-eviction paths don't reach that comparison, so check specifically whether those paths independently validate too, not just the happy path.** That asymmetry is easy to miss, since the happy path looks completely safe on its own. This matters most for any multi-process engine with a real renderer/privileged-process trust boundary; it doesn't apply in the same shape to an architecture like Servo's, where the resource thread isn't separated from script by that kind of boundary. **Firefox** has exactly this kind of trust boundary (a sandboxed content process speaking IPC to an unsandboxed parent process that owns the registry), and re-validates the algorithm/value shape on the trusted side independently of whatever the content-process-side WebIDL layer already checked.

4. **Gate `getFile()` per *handle*, not per *entry*.** The spec makes this explicit — a
   `FileSystemFileHandle` addressing a COS entry carries a
   [`may read`](https://wicg.github.io/cross-origin-storage/#creating-and-writing-files) flag,
   true for a handle from a read request and false for one from a create request until
   `verify and store` succeeds for that same handle — but it is worth calling out because the
   per-entry shortcut is the natural thing to write and its failure mode is invisible in testing.

   A create request returns a handle whether or not the entry already exists and is already
   written. So "is the entry written? then serve the bytes" turns every create request into a
   read: any origin can ask for a handle for a hash it has never written, call `getFile()`, and
   learn the contents — without satisfying `origins`, PHL membership, or GREASE'ing, all of which
   are enforced on the read path only. Requiring the caller to supply the correct bytes first is
   what makes a create-obtained read harmless: it discloses nothing the caller did not already
   have.

   **This is the kind of bug ordinary tests do not catch.** In the common single-origin round
   trip, the handle that wrote the entry *is* the handle reading it, so a per-entry check passes
   every such test. Test it with two distinct origins, one of which never writes.

5. **Periodically self-audit code you have already written for exactly this category of gap — don't assume a first implementation pass or a single review caught everything, even your own.** A "defer this for later" note is not a plan — it's a note that nothing else forces you to ever act on. Without a deliberate, periodic forcing function to go back and check what's still marked deferred, "later" has no natural trigger to actually arrive. If your own process doesn't already have a scheduled or checklist-driven equivalent, build one — a fresh pass explicitly looking for your own codebase's `TODO`/`FIXME`/"Phase 1 limitation"-style markers, cross-checked against a document exactly like this one's list of known-important gaps, catches an entire category of issue that ordinary "does the feature work" development and review does not reliably surface.

## 11. GC/memory-safety pitfalls specific to embedding in a JS engine

**The transferable lesson, regardless of engine:** if your browser embeds a JS engine with its own GC and your native/host-language code ever constructs values that reference GC-managed JS objects (a JS value, a rooted handle, anything the GC needs to trace), find out early what your engine's equivalent safety mechanism is — and **make sure your normal local development build configuration actually exercises it**, not just CI. A GC-safety bug that only gets caught in CI, after a whole feature is otherwise "done" locally, costs much more to fix than one caught at the point it was introduced.

**Servo** (Rust/SpiderMonkey) uses a custom Rust lint (`crown`) enforcing that any value containing a raw, unrooted handle to a GC-managed JS object is never held in a way the garbage collector can't see and potentially invalidate out from under you. **This lint needs to run in local development builds, not just CI** — a local build with it disabled (a deliberate speed tradeoff, since it requires a separately-installed compiler plugin) lets GC-safety violations in JS-adjacent dictionary/enum construction (constructing a value and holding it in a named local variable, rather than constructing-and-immediately-consuming it as part of one expression) compile and run locally without being caught until CI. The fix in every case is mechanical: never bind the flagged value to a `let`/function-parameter; construct it inline as part of the expression that immediately consumes it (a direct function-call argument, or a receiver for an immediate method call). (V8 has its own equivalent rules and lint tooling around `HandleScope`/`Local<>`; SpiderMonkey embeddings elsewhere typically use `Rooted<T>`/tracing conventions — the general shape of this hazard is common to any GC'd-engine embedding, not just Servo's specific setup.)

**Ladybird** (C++, its own custom GC) didn't hit a comparable bug during COS's implementation. That's less a demonstrated advantage than a case of following an already-established construction pattern for GC-tracked objects elsewhere in the codebase (native construction via a precedent function, capturing `GC::Ref`s by value in lambdas) rather than inventing a new one — the same "find your engine's rooting convention early" lesson above, just paid for with precedent-following instead of a dedicated lint catching a violation.

## 12. Testing strategy

**A real spec-conformance WPT suite for this feature already exists — use it, don't write your own from scratch.** [`web-platform-tests/wpt#61811`](https://github.com/web-platform-tests/wpt/pull/61811) is the in-flight pull request adding the `cross-origin-storage/` test directory to the shared WPT repo; all four implementations referenced throughout this document ran against it. It hasn't merged yet as of this writing, so your engine's regular WPT sync won't pick it up automatically — vendor it in manually instead: copy both the PR's `cross-origin-storage/` directory *and* the separately-located `interfaces/cross-origin-storage.idl` (`idlharness.js` fetches that one independently; missing it breaks every worker-global test with a fetch error, not a real failure) into your local WPT checkout, then regenerate your manifest. Treat this as a temporary local copy for validation, not something to commit permanently — once the PR actually merges, your engine's normal WPT sync process supersedes it; revert your local vendoring (including the manifest diff) at that point so your feature work stays scoped to the implementation itself. Check the PR's own status before you start — it may have already merged by the time you read this, in which case a normal sync is all you need.

**Unit-test the registry logic directly, without going through script/IPC at all** — call your registry service's internal functions directly with different origin values, hash values, and grants. This is where the bulk of your test coverage should live; it's fast, deterministic, and can exercise edge cases (concurrent-write races, ceiling parsing, budget exhaustion, eviction ordering) that are awkward to trigger reliably through a real browser instance. Concretely, make sure you have real coverage for:
- A hash confirmed present on your bundled PHL snapshot *is* disclosed through the global grant to a different origin; a hash *not* present is *not*, even though both were written with `origins: '*'`.
- Actual different origin values for writer vs. reader in every disclosure test — same-site-but-different-origin, genuinely-different-site, listed vs. not-listed, etc. — not just single-origin round-trips.
- **The grants are additive in both directions, tested with content deliberately *not* on your PHL snapshot**: an `origins: '*'` write over a list-scoped entry must leave every listed origin still able to read it, and a list written over an already-globally-disclosable entry must not withdraw the global grant. Using listed content here makes the test pass under a broken one-enum model; see [§4](#sec-4).
- **A create request registers nothing**: a read of a hash whose only write is in flight is an ordinary `NotFoundError`, for the writing origin as much as for anyone else, and an abandoned create handle blocks nothing. See [§2](#sec-2).
- **Ceiling parsing fails closed as a whole**: `"*"`, an unparseable token, or an absent header all authorize nobody, and one bad token in an otherwise-valid list empties the ceiling rather than being skipped. See [§4](#sec-4).
- GREASE'ing: an eligible small entry is *sometimes* GREASEd; a large entry is *never* GREASEd, regardless of how many trials you run.
- Every rejection path reports the *stable nominal* quota number, never a number that varies with real disk state.
- A failed write leaves the hash absent (a later plain read gets `NotFoundError`) — **and, separately, a failed write does not disturb a *concurrent, still-outstanding* sibling writer of the same hash**, whether that sibling later succeeds or is still in flight. Both halves matter; see [§2](#sec-2). Under the current model the second half holds because a failure removes nothing, but keep the test: it is the assertion that catches a reintroduction of registry state on the create path. Test the same pairing for an explicit `abort()`, not just a `close()` failure.

**Firefox:** unit tests run directly against the registry/rate-limiter singletons on the actual PBackground thread (no script/IPC involved, per this section's opening advice) cover: the create/read lifecycle; the concurrent-writer-race invariant (both halves of the bullet above, via `VerifyAndStore` directly); disclosure across all three grants with real distinct origins; the additive-upgrade rule; and a real rate-limiter burst exhaustion to denial, done as a tight in-process loop against the real limiter (a direct instance of this section's own "bulk/loop-shaped scenarios can be unreliable through browser automation" advice). **A portable lesson from building this suite: a bare unit-test process may not trigger your platform's normal crypto-subsystem startup path — initialize it explicitly before calling into hashing primitives directly** (Gecko: raw NSS calls need explicit initialization in a bare unit-test process). Also worth watching for: asserting a PHL/GREASE-gated outcome against a fabricated hash that could never legitimately pass that gate reproduces the very flakiness this section's own "assert the shape, not an exact boundary" advice warns about, just for a gate instead of a token bucket. What still isn't unit-tested: the PHL-membership bullet just above (needs a real preimage, see this section's own explanation of why), and persistence/storage-budget eviction's disk-touching paths.

**Three lessons on testing time- and resource-bounded logic** — **Ladybird:**
- **A real wall-clock token bucket is flakier to assert exactly than it looks.** In a tight loop, a refill tick can land between two consumes and let one extra request through non-deterministically. Assert the *shape* of the behavior (denial eventually happens; success count falls within `[capacity, capacity + small slack]`), not an exact boundary count — an exact-count assertion will intermittently fail for reasons that have nothing to do with a real bug.
- **Bulk/loop-shaped scenarios (rate-limit exhaustion, quota exhaustion via many writes) can be outright unreliable through a real browser-automation harness, not just slow.** A headless test harness's "is this page idle yet" heuristic isn't designed for a long-running script loop still legitimately working, and can tear the page down mid-test. This sharpens the "unit-test the registry directly" advice above with a concrete reason beyond speed: for scenarios shaped like this, going through full browser automation may not even be reliable, independent of how fast it runs.
- **Resource-limit tests usually don't need mocking.** Testing "an absurdly large `truncate()` gets correctly capped" doesn't necessarily need a dependency-injection seam for the limit, to avoid actually doing something slow or dangerous. A sparse `truncate()` to well beyond any realistic per-origin budget is typically a same-millisecond, metadata-only operation on a real filesystem. Verify your specific "huge size" operation is actually cheap on your target filesystems, then pick a size safely beyond any plausible real machine's limit, and test against the real thing.

**If you default-enable the feature on your branch, expect your engine's web-exposed API listing tests to fail, and rebaseline them deliberately.** Most engines have a test that enumerates every interface and attribute exposed to script, precisely so that adding surface is never silent. Turning COS on by default adds `CrossOriginStorageManager`, `navigator.crossOriginStorage` and the `cross-origin-storage` policy-controlled feature to those listings, in the window *and* every worker variant, and — if your engine has a separate "stable-release-mode" listing — in that one too. This is expected and the rebaseline is the correct response; the thing to watch is that regenerating baselines wholesale can also rewrite or delete *unrelated* ones your tooling considers redundant. Review the regenerated diff and revert anything that is not about your feature, rather than carrying hundreds of unrelated deletions along in the change. **Chromium:** four listing tests plus their stable-mode variants; `--reset-results` additionally deleted three unrelated baselines that had to be restored by hand.

**Also test at least one real, genuinely cross-origin scenario through the actual browser**, not just unit tests. It's easy to build an entire browser-level smoke-test suite (write/read round-trips, `seek()`/`truncate()` correctness, oversized-buffer rejection, large streamed writes) that never once exercises actual cross-origin disclosure or the PHL, because every test happens to write and read from the same origin/session for convenience. Unit tests proving the *logic* is correct are not the same as proof it works end-to-end through your real IPC boundary and JS bindings with two genuinely different origins. Concretely:
- Stand up two actually-different origins (different port is enough — same-origin policy is scheme+host+port; two different ports on `127.0.0.1` are two different origins, and loopback addresses are treated as secure contexts by every major browser's Secure Contexts implementation, so you don't need real TLS certs for this).
- Use a **real** PHL-listed resource with a **known preimage** — you cannot construct arbitrary bytes that hash to an arbitrary target value, so pick a hash from your PHL's "manually curated" entries (ones with documented provenance/source URLs in the PHL data itself), fetch the real content, and verify its digest matches before you build a test around it.
- From origin A: store that resource with `origins: '*'`, and *also* store some arbitrary (definitely-not-listed) content the same way, as a paired positive/negative case.
- From origin B (a genuinely different origin — reload/navigate, don't just call from a different script context on the same page): confirm the PHL-listed resource is readable and byte-for-byte correct, and confirm the non-listed one correctly fails closed (and check the *specific* rejection reason your implementation actually uses — don't assume; verify against your own source rather than guessing the DOMException name).

**Firefox:** this specific genuine-cross-origin-with-known-preimage test is still an open item. A useful technique for this class of scenario, worth adding to this section in its own right: for cases this document's own spec-conformance test suite structurally cannot reach (persistence surviving a real process restart, [§7](#sec-7); a browser-chrome-level integration like clear-data, [§16](#sec-16)) — as opposed to anything reachable from ordinary web content — drive the actual built browser through its remote-automation/WebDriver-style protocol (Gecko: Marionette, via the `marionette_driver` Python package already used by the platform's own test harness): launch the real binary against a real, persistent (not auto-deleted) profile directory, execute privileged/chrome-context script against it directly, and fully quit-and-relaunch the same binary against the same profile to actually exercise a restart. This is a genuinely different tool from unit-testing the registry directly (the bulk of this section's own advice, still correct and still where most coverage should live) and from an in-browser spec-conformance test (which can only ever exercise what's reachable from ordinary web-content script, in one continuous process lifetime) — it fills the gap of "reachable only from chrome/privileged context, or spanning a process boundary this feature's own spec-facing tests never cross." If your platform has an equivalent remote-automation protocol (most engines with any automated-testing story at all do, even if not literally WebDriver), it's worth having in your toolbox specifically for this class of check. **One caveat:** a script like this, run by hand and not checked into the tree as a repeatable, CI-run test, is not a substitute for an actual regression test a future change could break silently — treat it as a strong argument for why the equivalent should eventually become a checked-in test, not as equivalent to having written one.

## 13. Complexity/scale summary

| Operation | Naive complexity | Better approach | Why it matters |
|---|---|---|---|
| Total bytes used / per-origin bytes used | O(n) scan, on every write | O(1), incrementally maintained | Called on every single write |
| Eviction candidate selection | O(n log n) collect+sort, every eviction pass | O(log n) per removal, via an ordered index | Eviction is not rare at scale |
| PHL membership lookup | O(n) or O(1) hash set (memory-heavy) | O(log n) binary search over a sorted packed array | Hundreds of thousands of entries, read-only after load |
| Cross-process read-result transfer, in-process case *(Servo only — see [§9](#sec-9))* | O(bytes) copy per hop | O(1) refcount bump, one real copy only at final materialization | Payloads can be multi-hundred-MiB |
| Read-path in-memory caching *(Firefox: deliberately not built)* | A full disk read on every single `getFile()` call, even for the same entry read repeatedly | An in-process resident-bytes cache, à la Servo's [§9](#sec-9) `Arc<Vec<u8>>` | Named here as an explicit, currently-accepted gap, not an oversight — every `getFile()` currently re-reads the persisted file from disk, unconditionally |
| Rate-limiter memory | O(distinct origins ever seen), unbounded | O(1) bounded (LRU-capped map) | Long-running sessions visiting many sites |

|---|---|---|
| Pending-entry staleness timeout | 5 minutes | When an unfinished write is treated as abandoned |
| Read-probe limits | **Removed, see [§5](#sec-5)** | The former 2000-burst / 20-per-second figures were a throughput limit being mistaken for a privacy defense; the replacement is under discussion in [#72](https://github.com/WICG/cross-origin-storage/issues/72) / [#73](https://github.com/WICG/cross-origin-storage/pull/73) |

## 15. Suggested implementation order

1. Data model + persistence (per-entry files or equivalent, atomic writes), with entries created only by `verify and store` and the three additive grants stored as separate fields ([§2](#sec-2), [§4](#sec-4)). Get this solid before anything else — everything builds on it, and both of these are much cheaper to get right now than to unpick later.
2. The same-site baseline only (simplest grant, reuses existing same-site logic). Full read/write round-trip, single-origin, working end to end through your real IPC/script boundary before adding anything else. **If your engine has genuinely separate script-hosting process types** (not just Window vs. Worker as a JS-level distinction — see [§1](#sec-1)), decide explicitly and early whether this step is scoped to just the main script-hosting process or all of them; deferring Worker/SharedWorker support is only cheap to retrofit later if a per-worker-process route to shared browser state already exists for something else.
3. Rate limiting for reads and writes — bounded from day one, not retrofitted. Note this is abuse resistance, **not** the privacy defense; the cross-origin probe budget that bounds identifier width is a separate mechanism still being settled, see [§5](#sec-5).
4. Storage budget + eviction, including the running-totals/incremental-index performance work from the start — don't ship the O(n)/O(n log n) version even temporarily if you can avoid it; it's a straightforward rewrite later but easy to forget once it "works."
5. The origins list + LRU merge behavior, and the `Cross-Origin-Storage-Allow-Origin` ceiling that bounds it ([§4](#sec-4)) — the ceiling belongs with the list rather than after it, since a list implemented without one is a disclosure any injected script can widen.
6. The global grant: PHL integration first (get the fetch/verify/refresh pipeline solid and automated, or a placeholder that fails closed if you're deferring it), then GREASE'ing.
7. Streaming the write transfer to your shared registry service ([§3](#sec-3)) — after correctness is solid elsewhere, since it's a pure performance/memory optimization that's easy to get subtly wrong (see the integrity bug in [§3](#sec-3)) if done under time pressure.
8. Security review pass, specifically for: hash validation completeness across *every* recognized algorithm, unbounded-allocation paths reachable from a single script call (`seek()`/`truncate()` and anywhere else your API surface accepts a caller-controlled size), re-validation on the trusted side of anything used for filesystem-path construction if your engine has a renderer/privileged-process trust boundary (see [§10](#sec-10)), and whether anything on the create path is observable to the caller before bytes have been supplied and verified ([§2](#sec-2)).
9. A genuine two-origin, PHL-aware browser-level test, in addition to unit tests — don't consider this feature done without one.

## 16. Clear-data / "Forget This Site" integration — **Firefox only; a genuinely new problem neither other implementation's notes address**

Every browser has some existing mechanism for "delete what this site (or everything) has stored" — a settings-UI action, a privacy API, whatever backs "Clear Recent History" or "Forget About This Site." COS needs to plug into it, and this section exists because doing so surfaces a design question the rest of this document's model doesn't resolve on its own: **the browser's existing site-data-clearing machinery is almost certainly built around the assumption that stored data belongs to exactly one site.** COS entries don't — that's the entire premise of content-addressable sharing ([§2](#sec-2)). A naive port of "delete everything this principal/site owns" breaks the moment two independent, unrelated sites have each legitimately stored the identical bytes under the same hash, which is not an edge case — it's the feature working as intended.

**Two structurally different operations, only one of which is actually ambiguous:**

- **A full wipe** ("Clear Recent History" → "Everything," a dedicated privacy-settings toggle, or your platform's equivalent broad action) is unambiguous: delete every entry, in memory and on disk, unconditionally. No design question here — implement it as a plain, total reset of the registry.
- **A site-scoped clear** ("Forget About This Site," or the site-data-scoped part of a "Clear Cookies and Site Data" action) is where the real design question lives, because an entry can have several storing origins and an origins list naming still other origins. **Two genuinely different, both-defensible policies:**
  1. **Revoke-and-GC (Firefox's choice):** strip the target site's association from every entry it's connected to — remove it from that entry's storing-origins set, its storing-*sites* set (kept in lockstep, per [§2](#sec-2)'s glossary distinction between storing origins and disclosure scope), and any explicit `origins`-list disclosure grant naming it — and only actually delete the entry outright if that removal leaves it with **no storing origin left at all**. An entry a *different*, uncleared site also legitimately stored keeps that other site's copy untouched. This is a refcount-style policy: the bytes persist exactly as long as at least one origin still has a genuine storing relationship to them.
  2. **Delete-if-involved:** delete any entry the target site's origin ever appears in, full stop, even if other origins also stored the identical bytes. Strictly more private in the sense that zero trace of the cleared site's involvement survives anywhere in the registry — but it means clearing site A's data can silently delete data site B genuinely still has and depends on, purely as a side effect of an action B was never part of and never asked for.
  
  **Neither the spec nor the explainer defines this** — it's a real, open implementation choice, not something you can look up. Revoke-and-GC was chosen on the reasoning that surprising an *uncleared* site by deleting its data is a worse failure mode than a cleared site's bytes technically persisting under a different, legitimate owner's storing relationship — but weigh this for your own browser's own privacy posture rather than treating either answer as obviously correct. If your organization's threat model treats "zero trace, ever, no matter the collateral cost to an unrelated site" as the binding constraint, delete-if-involved is the more defensible choice for you specifically.

**Site-scoped matching should be host-suffix-based, matching whatever convention your platform's *existing* clear-data API already uses for the same purpose** (e.g., "`foo.example.com` matches a clear request for `example.com`") — not a fresh eTLD+1/Public-Suffix-List computation of your own. Your platform almost certainly already has this exact logic for its non-COS clear-data paths (cookies, IndexedDB, cache); reuse its convention rather than inventing a subtly different one, for the same "don't write new same-site logic when your cookie jar already has it correctly" reason [§4](#sec-4) gives for same-site comparisons generally.

**A concrete architectural wrinkle if your registry lives on a thread/process your browser's clear-data machinery doesn't already have a direct line to** (see [§1](#sec-1)): clear-data actions typically originate from a privileged UI-adjacent context (a settings page, a toolbar action) that may not be the same thread the registry itself requires. If so, you need a small dedicated bridge — a scriptable service reachable from that privileged context, which dispatches the actual mutation onto the registry's own required thread and resolves/signals completion back once it's done, rather than either (a) relaxing the registry's own threading requirement just for this one caller, or (b) blocking the calling thread synchronously waiting for the registry's thread to respond. Treat a null/unavailable registry-owning thread at this bridge (nothing has ever touched COS in this session, so the thread hosting it was never even started) as a legitimate, harmless no-op — there's provably nothing to clear.

**A real, documented, currently-unresolved modeling gap this design creates, worth naming explicitly rather than discovering by surprise:** [§6](#sec-6)'s storage-budget usage is attributed to whichever origin's write first transitioned an entry to written. If a *site-scoped, partial* revoke-and-GC removes specifically that origin from an entry's storing-origins set while other storing origins remain, the usage credit charged against the removed origin's own budget share does not transfer to whichever origin is now first in the (now-shorter) storing-origins list, and does not get released back to the global total either — it simply goes stale. This is rare in practice (it needs multiple origins to have genuinely, independently stored byte-identical content, *and* a site-scoped clear to remove specifically the one attributed with the charge, while others remain), and it's bounded rather than actively harmful (the stale credit can't grow, it just stops accurately reflecting reality) — but a more precise implementation should either reattribute the charge to the new first storing origin on a partial revoke, or move to a model that doesn't rely on single-origin attribution for shared entries at all. Firefox's implementation does neither yet; this paragraph exists so the next implementer either solves it more completely or at least makes the same simplification deliberately, with eyes open, rather than being surprised by it during their own review.

**Testing note, extending [§12](#sec-12):** the full-wipe path is straightforward to verify end-to-end (write an entry, invoke the clear action, confirm it's gone). The site-scoped partial-revoke path is harder to test at the full actor/IPC level, for the same reason [§12](#sec-12) already flags for a real cross-origin PHL test: it needs two *actually distinct* origins to have each legitimately stored the same content, then a site-scoped clear against only one of them, then confirmation that the *other* origin's copy survives untouched — a scenario a single privileged-context automation script (system/chrome principal throughout, as [§12](#sec-12) also notes) cannot produce on its own without real content-page navigation to two distinct origins. **The underlying logic doesn't need that, though: unit-test the site-removal function directly** (per [§12](#sec-12)'s own opening advice), with two distinct `Entry` objects/two distinct storing-site strings constructed directly, rather than requiring a real browser round trip at all — this covers the actual revoke-and-GC mechanism itself, leaving only the actor/IPC plumbing on top of it to verify through the heavier browser-automation route.

**A sharp, easy-to-make test-authoring mistake when exercising this directly:** site-scoped matching operates on the *site* (scheme + eTLD+1, [§4](#sec-4)'s same-site computation), not an origin's full host. If your test constructs an origin like `https://sole-owner.example.com` and then invokes the site-removal function with that same string (`"sole-owner.example.com"`) rather than the actual computed site (`"example.com"`), the host-suffix match will never fire — `example.com` is not a subdomain of `sole-owner.example.com`, only the reverse — and the clear operation silently no-ops instead of throwing. The test then fails on its own follow-up assertion ("the entry should be gone now") with a result that looks at first glance like an implementation bug in the removal logic, when it's actually just the test passing the wrong string. Always pass the same site-shaped value your `GetSite()`/same-site helper would actually compute for that origin, not the origin's own host.
